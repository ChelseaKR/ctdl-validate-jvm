# 4. The port may lead the pinned reference, in a corpus that says so

## Status

Accepted

## Context

ADR 0003 pins parity to a released reference artifact and makes byte equality
against it the gate. Its consequences section anticipated the port falling
*behind* the reference and accepted that. It did not anticipate the port
running *ahead* of it, which is what a rule fix in this repository produces
whenever the reference has not shipped the same fix in a release.

That case arrived with `CONCEPT_RANGE_CONFLICT`. CTDL declares a reference to
a term from one of its own concept schemes two incompatible ways — 46
properties range on `ceterms:CredentialAlignmentObject`, 45 on `skos:Concept`
— and the published Registry corpus encodes both as an alignment object.
Calling that a `RANGE_VIOLATION` failed 36 of the 120 published documents in
the 2026-08-15 survey. The reference has the fix on `main`; no released
version carries it, so the pin cannot be bumped to reach it.

Three options were on the table:

1. Don't fix the port until the reference releases. The tool keeps reporting
   Credential Engine's own dominant encoding as an error, on real documents,
   for as long as someone else's release schedule takes.
2. Fix the port and add no fixture. Parity stays green — the corpus contained
   no concept-valued property at all, which is exactly why parity never
   caught the defect — and the divergence is invisible until it surprises
   someone.
3. Fix the port and record the divergence as data, in a corpus whose only
   purpose is to bound it.

Option 2 is what the repository would have done by default, and it is the
worst of the three: a green build that is green because nothing looks.

## Decision

- `parity/fixtures/` remains byte equality against the pinned release, with no
  exemptions, exclusions, or allowances. Nothing about this ADR weakens it.
- `parity/ahead/fixtures/` holds payloads where this port answers differently
  on purpose. `parity/ahead/reference/` records what the pinned release says
  about them, generated by `tools/generate_expectations.py` and re-checked by
  the same CI job as `parity/expected/`, so the baseline is measured and not
  remembered.
- **No Java-side golden file is written for these.** Freezing this
  implementation's own output is the self-comparison ADR 0003 rules out.
  `AheadOfReferenceTest` asserts the *shape* of the divergence instead: same
  number of findings, in the same order, each one either identical to the
  reference's or a single declared substitution — a `RANGE_VIOLATION`/ERROR
  becoming a `CONCEPT_RANGE_CONFLICT`/INFO on the same entity, property, and
  value, for a property the vendored snapshot marks `meta:targetScheme`.
- **The corpus is self-expiring.** When the pin is bumped to a release
  carrying the fix, the reference stops disagreeing and the suite fails,
  which is the instruction to move the fixture into `parity/fixtures/` and
  delete the `parity/ahead/` entry. A divergence record that outlives its
  divergence is a lie, so it is arranged not to survive one.
- Every fixture in `parity/ahead/` needs the divergence to be real: a fixture
  that produces no substitution fails, rather than sitting there as a
  parity fixture filed in the wrong place.

## Consequences

- The port can fix a defect on real data without waiting on someone else's
  release, and without any of it being silent.
- The set of things this port is allowed to do differently is enumerated in
  one directory and one test. Widening it by a single finding is a red build,
  which is a stronger property than "the concept-range rule is right" — it
  bounds the whole class.
- The mechanism is deliberately unpleasant to grow. Each entry costs a
  fixture, a recorded reference document, and a justification in this ADR's
  terms, and the intended steady state is zero entries.
- The comparison has been broken on purpose and watched to fail, the same way
  `ParityTest` and `BreakTheGateTest` are, so it is not trusted on faith.
