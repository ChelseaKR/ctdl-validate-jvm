# 3. Parity is byte equality against a pinned reference release

## Status

Accepted

## Context

"The two implementations agree" can mean many things, and the weak versions
are worthless. Agreeing on the number of findings, or on the set of codes,
would let a wrong severity, a wrong entity label, a missing citation, or a
reordered report pass unnoticed — and those are exactly the failures a port
produces.

There is a second trap. If the expected results are written by hand, or
generated once from the Java implementation and then frozen, the suite is
comparing the port against itself and will happily certify a shared mistake.

A third question is what to compare *against*: the reference's `main` branch
moves, and a rule set that moves underneath the expectations makes a red
build ambiguous between "the port is wrong" and "upstream changed".

## Decision

- **Parity is string equality** over a document containing the exit code, the
  document-level error if any, every field of every finding including its
  rule citation and retrieval date, the order the findings come out in, and
  the plain-text report verbatim. Only the tool's name and version are
  excluded, because those are the only things the two implementations are
  entitled to differ about.
- **The expectations are generated by running the reference implementation**,
  by `tools/generate_expectations.py`, which imports it and calls it. No
  expectation is authored by hand.
- **CI regenerates them and fails on any diff**, so a stale expectation is a
  red build rather than a silent downgrade of the whole property.
- **The reference is pinned to a released PyPI artifact by version and
  hash**, in `parity/reference-requirements.txt`, and excluded from
  Dependabot. Bumping it is a review of a rule-set change, not a dependency
  chore.
- **Disagreement fails the build.** `ParityTest` is part of `verify`, not an
  advisory report.

## Consequences

- The suite catches things a looser comparison would not, and did: `repr()`
  formatting, code-point versus UTF-16 sort order, and JSON serialization
  details were all found by a red parity test rather than by review.
- The comparison is brittle in the useful direction. A cosmetic change to a
  message in either implementation fails the build, which is correct: the
  message is part of what a publisher reads.
- Malformed-JSON handling is out of scope, because the message there comes
  from the language's JSON parser rather than from the tool. Documents that
  parse but are not shapes the tool reads stay in scope; those messages are
  the tool's own.
- The port can fall behind the reference without any signal here. That is
  accepted: this is a demonstration repository, and a silently drifting pin
  is a smaller problem than a build that goes red because someone else
  shipped.
