# Improvement plan, 2026-08-28

Audit of `ctdl-validate-jvm` against its own README promises, the four open
issues, and the five open PRs. Every claim below was verified in this
repository before it was written down; where verification contradicted the
premise the plan says so.

## What was verified first

- `./gradlew verify` is green on `main` (exit 0, Temurin 21). A first run
  exited 1 for an environment reason only, Gradle defaulting to JVM 11, which
  is not a repository defect.
- The parity harness is honest. `parity/expected/` is generated by the Python
  reference, CI reinstalls the pin with `--require-hashes` and regenerates,
  comparison is whole-document string equality, and
  `ParityTest.theGateItselfHasBeenBroken` corrupts a severity and asserts the
  comparison notices.
- The vendored CTDL and CTDL-ASN snapshots hash exactly to the four SHA-256
  values in `src/main/resources/vendor/SOURCES.md`.
- Twenty finding codes are constructible, parsed out of `src/main/java` rather
  than read off `FindingCodes.ALL`: 20 distinct literals, 21 construction
  sites, zero sites with a non-literal code. All 20 fire: 19 appear in
  `parity/expected/`, so deleting the rule that emits one breaks byte equality;
  the twentieth, `CONCEPT_RANGE_CONFLICT`, is held by `parity/ahead/` and
  `ConceptRangeConflictTest`. No dead rule.

## Phase 1: the parity gate is blind to a rule it does not have

`ParityTest.corpusCoversEveryCode` builds its expected set from
`FindingCodes.ALL`, a list maintained inside this port. A rule the reference
has and the port never learned about is therefore invisible: it is absent from
the port's list, absent from the port's output, and absent from
`parity/expected/` unless a fixture happens to reach it. The corpus-coverage
test passes, and CI is green on a port that is missing a rule.

Two changes, in the direction of deriving the answer instead of maintaining it:

1. `FindingCodes.ALL` stops being trusted. A new test parses every
   `new Finding("...")` site out of `src/main/java` and fails if the maintained
   list and the source disagree, in either direction. The list may stay for
   grouping and documentation; it can no longer drift.
2. The reference's own code set becomes a recorded, regenerated fact.
   `tools/generate_expectations.py` already imports the pinned release; it now
   also parses that installed package's source for its finding codes and writes
   `parity/reference-codes.json`. CI's existing parity job regenerates it and
   `git diff --exit-code`s it alongside `parity/expected/`, so it cannot be
   hand-maintained or allowed to decay.

`ParityTest` then compares the two derived sets and requires every difference
to be declared, in either direction, with a reason. A code the reference emits
and the port does not is the port being behind; a code the port emits and the
reference does not is the port being ahead. Both are reportable. An undeclared
difference in either direction fails the build.

## Phase 2: two rules where the port raises an ERROR the reference does not

Verified by running three probe documents through the port, the pinned
reference 0.1.0, the latest release 0.2.1, and the reference's `origin/main`:

| document | port | 0.1.0 | 0.2.1 | reference HEAD |
|---|---|---|---|---|
| `Collection ceterms:hasMember Course` | ERROR `RANGE_VIOLATION` | same | same | no finding |
| `CompetencyFramework ceterms:previousVersion CompetencyFramework` | ERROR `RANGE_VIOLATION` | same | same | INFO `VERSION_RANGE_CONFLICT` |

The port agrees with the pinned release exactly, which is what the parity suite
is for and is evidence the suite works. Neither fix is in any released version:
both landed upstream in an unreleased commit, so bumping the pin cannot reach
them and `parity/ahead/` (ADR 0004) is the only available mechanism.

### 2a. `rdfs:Resource` is the class of everything

Settled by published text, in three independent places:

- RDF Schema 1.1, W3C Recommendation 25 February 2014, section 3.1: "All
  things described by RDF are called resources, and are instances of the class
  `rdfs:Resource`." and "This is the class of everything. All other classes are
  subclasses of this class."
- The vendored CTDL encoding declares `schema:rangeIncludes` of
  `ceterms:hasMember` as exactly `["rdfs:Resource"]`, of `owl:sameAs` as
  exactly `["rdfs:Resource"]`, and of `ceterms:isSimilarTo` as a list of 84
  terms, 83 of them distinct, that includes it. `schema:rangeIncludes` is a
  disjunction of expected types, so a disjunct that admits everything makes the
  union admit everything.
- CTDL's own published `rdfs:comment` on `ceterms:hasMember` is "Resource in a
  Collection", and the `dct:description` on `ceterms:isSimilarTo` is "The
  property is generally applicable in describing the similarity between any two
  entities."

And the mechanical fact that makes the port's behaviour an inversion rather
than a judgement call: `rdfs:Resource` is not among the 150 classes the
vendored snapshot declares, and zero classes reach it by `rdfs:subClassOf`. So
matching a target's declared classes against it rejects every entity, when the
declaration admits every entity. The port is wrong, in the worse direction for
a validator. Adopt the reference's `UNIVERSAL_RANGE_TERMS` guard.

### 2b. `VERSION_RANGE_CONFLICT` is a conflict, not an error

Verified against the vendored encoding: `ceterms:latestVersion`,
`ceterms:nextVersion` and `ceterms:previousVersion` each declare a domain of 61
classes and a range of 55, the range is a strict subset of the domain in all
three, and all three drop the identical six classes: `ceasn:Competency`,
`ceasn:CompetencyFramework`, `ceasn:Rubric`, `ceterms:Collection`,
`ceterms:Pathway`, `ceterms:TransferValueProfile`.

For a dropped class the two declarations cannot both be satisfied: the domain
says an instance may have a version, the range says that version may not be an
instance of the same class. Published wording does not settle which of the two
declarations is wrong, and this plan does not pick a side. What it rules out is
the ERROR: the document satisfies a published declaration, and reporting it as
a defect would tell a publisher to fix something with nothing to fix it to.
INFO, non-gating, matching how `RANGE_DOCS_CONFLICT` and
`CONCEPT_RANGE_CONFLICT` already dispose of published sources that disagree.

The finding is narrowed to a link between two entities of the same dropped
class, which is the only shape where the range omission is certainly the
disagreement rather than an ordinary out-of-range reference.

### 2c. Recorded, not fixed: `owl:sameAs` domain

`owl:sameAs` declares `schema:domainIncludes` as exactly `["rdfs:Resource"]`,
and the port reports `DOMAIN_VIOLATION` / ERROR for any subject using it. By
the identical published reasoning as 2a that is also a false ERROR. It is left
alone here, because the reference has not fixed it either -- `origin/main`
still emits it -- and the README is explicit that this repository is not where
a rule change belongs. Fixing it here would be this port inventing a
disposition the specification work has not made. Recorded in the README limits
and reported upstream instead.

## Phase 3: the ahead-of-reference contract has to widen, carefully

`AheadOfReferenceTest` currently permits exactly one substitution,
`RANGE_VIOLATION`/ERROR becoming `CONCEPT_RANGE_CONFLICT`/INFO, and requires
the finding counts to match ("never add or drop one"). Phase 2 needs two more
shapes: a second substitution, and a withdrawal, since the universal-range fix
removes a finding rather than restating it.

The generalisation keeps the property that makes the current test worth having:
every permitted disposition is gated on a predicate derived from the vendored
snapshot, so a substitution can never be justified by anything but the schema.
A disposition table replaces the two constants, each row carrying the
reference's code and severity, the port's code and severity or a withdrawal,
and the schema-derived predicate that says which properties it may touch.

## Phase 4: three gates that pass having scanned nothing

- `OfflineGuaranteeTest.noNetworkingTypesAreReferenced` walks
  `build/classes/java/main` and asserts only that the directory exists. An
  empty directory scans zero class files and passes.
- `OfflineGuaranteeTest.noModelCalls` walks `src/main/java` with no assertion
  that it read anything at all.
- `DeterminismTest.repeatedRunsAgree` asserts inside a loop over
  `Files.list(parity/fixtures)`. An empty directory runs zero assertions and
  passes.

Each gets a counter and a floor. This is the cheapest class of defect in the
audit and the one the governing rule names first.

## Phase 5: documentation that has drifted from the code

The README says "All five checks and all 19 codes are here" in one place and
"All 20 do" in another, and calls the corpus "22 CTDL JSON-LD payloads" in one
place and "21 payloads" in two others. Actual counts: 20 codes, 22 fixtures.
Corrected against the parsed source and the directory listing rather than
against either prose claim.
