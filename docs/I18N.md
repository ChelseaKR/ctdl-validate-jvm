# Internationalization

**State: N/A, and it is a constraint rather than an omission.**

## The decision

This tool's operator output — every finding message, every rule citation, every
line of the text report, and the two stderr messages — is English only, and
translating any of it here would be a defect.

The reason is specific to this repository rather than general. `ParityTest`
compares this implementation's output against
[`ChelseaKR/ctdl-validate`](https://github.com/ChelseaKR/ctdl-validate) byte for
byte, over every fixture, including the human-readable `text_report`. That
comparison is the only thing this repository exists to demonstrate. A translated
message is a message the reference does not produce, so it turns a green parity
run red — not because a rule is wrong, which is the one thing a red parity run
is supposed to mean, but because someone localized a string on one side of the
comparison.

The citation text is a stronger case still. Every finding carries a rule
citation that quotes Credential Engine's published sentences, retrieved on a
recorded date. `CONTRIBUTING.md` puts it under "Cited rules only": the wording is
the reference's, because it is Credential Engine's, and rewording it would make
the two implementations disagree about what a rule *says* rather than about what
it *decides*. Translating a citation would additionally be presenting a
paraphrase of a normative sentence as the sentence itself.

## What that means in practice

- No message catalogue, no locale negotiation, no `Locale`-sensitive formatting
  anywhere in the validator. There is nothing to translate against, deliberately.
- No locale-dependent behaviour, either. `CodePointOrder` sorts by Unicode code
  point rather than by any collation, because the reference sorts Python strings
  and Java's `String.compareTo` orders by UTF-16 code unit, which disagrees with
  it above the Basic Multilingual Plane. That is an internationalization-shaped
  bug fixed for a parity reason, and it is in the README.
- Input is not English-only and never was. CTDL language maps
  (`{"en-US": "..."}`) pass through untouched, entity names and labels in any
  language are read and echoed back into findings verbatim, and a payload in
  Spanish or Japanese validates exactly as one in English does. Only the tool's
  own sentences about it are English. The document is read as UTF-8 explicitly
  (`Files.readString(..., StandardCharsets.UTF_8)`), the sources compile with
  `-encoding UTF-8`, and `tools/generate_expectations.py` renders with
  `ensure_ascii=False`, so the two implementations are compared on non-ASCII
  bytes rather than on escapes.
- One thing that is *not* pinned, stated rather than glossed: `Cli.main` hands
  `System.out` and `System.err` to the reporter, so what the CLI writes is
  encoded with the JVM's own stdout charset. On the Java 17 floor that is the
  platform default rather than UTF-8, so a non-ASCII entity label can be
  mangled on the way out on a non-UTF-8 platform. Nothing in the test suite
  covers it, because `CliTest` supplies its own UTF-8 streams and never exercises
  the default. It is written down here rather than claimed to be handled.

## What would change this

Translation belongs in the sibling first, if ever. If the reference gains
localized messages, this port inherits them the same way it inherits every other
rule change: bump the pin, regenerate `parity/expected/`, and read the diff. Any
other order makes the two implementations disagree on purpose, which is the one
thing `parity/fixtures/` is not allowed to record.

The sibling's own `docs/I18N.md` reaches N/A from one of these two reasons: that
translating the wrapper text around untranslated cited rules would misattribute
wording to credreg.net. That reason holds here unchanged. What is added here is
the second one, which is this repository's alone: byte equality makes the
decision unrevisable locally. The sibling could choose to localize and would only
have to design around the citations; this port could not follow without breaking
the comparison it exists to be.
